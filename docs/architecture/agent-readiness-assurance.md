# Continuous Agent Readiness Assurance

Status: adopted architecture requirement
Source: arXiv:2607.21495
Owner: Factory OS

## Decision

Factory OS SHALL maintain continuous operational assurance for every registered agent and its runtime dependencies.

Readiness is necessary evidence for execution governance. It is never execution authority.

A technically ready agent MAY still be denied, deferred, modified, stepped up, or halted because mandate, purpose, model admissibility, policy, context, evidence, human authority, or consequence constraints are insufficient.

## Readiness contract

Every agent SHALL have a versioned readiness contract covering:

- model and model configuration
- language and dialect competence requirements
- tools and external APIs
- retrieval sources, indexes, schemas, and freshness
- credentials, identity bindings, and delegated permissions
- workflow and orchestration dependencies
- input and output contracts
- policy and governance dependencies
- owner, risk owner, escalation path, and service objectives
- test cadence and event-triggered assurance conditions

Contracts SHALL be machine-readable, provenance-bound, and included in dependency graph hashing.

## Failure taxonomy

Assurance SHALL detect and classify at minimum:

1. Model failure: unavailable, changed, degraded, incompatible, or outside MAL approval.
2. Tool/API failure: unavailable, changed contract, timeout, malformed result, or permission loss.
3. Retrieval failure: stale, missing, poisoned, semantically shifted, or schema-incompatible evidence.
4. Credential and identity failure: expired, revoked, over-broad, unbound, or inconsistent authority.
5. Output-contract failure: invalid schema, missing required fields, semantic mismatch, or unverifiable output.
6. Workflow failure: broken orchestration, ordering, state, retry, idempotency, or dependency conditions.
7. Semantic degradation: behavior remains syntactically valid while meaning, language representation, intent, or task performance degrades.
8. Ownership and governance failure: missing owner, expired review, absent escalation, policy drift, or unknown responsibility.

Unknown conditions SHALL fail closed for consequential execution.

## Assurance triggers

Factory OS SHALL evaluate readiness:

- before first commissioning
- periodically according to the readiness contract
- after model, prompt, policy, tool, schema, credential, retrieval, workflow, or ownership changes
- after incidents or anomalous outcomes
- before consequential execution when cached readiness evidence is stale or dependency hashes differ

## Architecture binding

Factory OS:
- registers agents, contracts, owners, dependencies, and assurance schedules
- maintains the living dependency graph
- detects dependency and configuration changes

Harness:
- exposes behavior-to-source and behavior-to-dependency mappings
- provides executable probes and contract tests

MAL:
- verifies model, configuration, language, dialect, domain, and exclusion admissibility

VAIG:
- evaluates readiness evidence, degradation signals, unknowns, and assurance quality

REHT:
- treats readiness as one required evidence class before consequential action
- SHALL NOT translate READY directly into execution clearance

RACS:
- enforces ALLOW, MODIFY, DEFER, DENY, STEP_UP, or HALT from the complete governance evaluation

Receipts:
- records assurance inputs, results, provenance, hashes, unknowns, and the decision relationship

## Receipt fields

Readiness evidence and execution receipts SHALL support:

- readiness_contract_id
- readiness_contract_version
- readiness_status
- readiness_evaluated_at
- readiness_valid_until
- dependency_graph_hash
- dependency_snapshot
- assurance_run_id
- assurance_trigger
- assurance_tests
- failed_dependencies
- degraded_dependencies
- unknown_conditions
- evidence_refs
- semantic_integrity_status
- mal_determination_ref

The readiness receipt and execution clearance receipt SHALL remain separate artifacts linked by immutable references.

## Invariants

- READY does not imply ALLOW.
- A dependency change invalidates readiness evidence tied to the previous dependency graph hash.
- Expired or unverifiable readiness evidence cannot authorize consequential execution.
- Semantic degradation is a first-class failure even when interfaces and schemas remain valid.
- Original language, provenance, ambiguity, and transformation history must remain traceable through assurance and execution.
- Assurance generated by an LLM cannot independently attest itself; consequential use requires deterministic checks or independent verification.
- Revocation of identity, credentials, policy approval, or model admissibility invalidates affected readiness evidence immediately.

## Minimum implementation order

1. Define the machine-readable readiness contract schema.
2. Extend the Factory OS agent registry with dependency graph and contract references.
3. Add event-triggered invalidation and periodic assurance runs.
4. Add VAIG readiness evidence ingestion and unknown-condition handling.
5. Add REHT rule: readiness required but insufficient for execution clearance.
6. Extend Receipts with the fields above and cross-artifact verification.
7. Add conformance tests proving READY cannot bypass mandate, authority, policy, MAL, or consequence controls.

## Validation requirement

Initial validation SHALL include dependency failure, silent semantic degradation, stale retrieval, revoked credentials, changed output schema, workflow drift, ownership expiry, and a technically healthy agent lacking execution authority.

Metrics SHALL include detection coverage, false-positive rate, false-negative rate, time to detection, time to diagnosis, recovery verification, and stale-readiness rejection.
