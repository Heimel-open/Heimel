# relAIon Personal Opportunity Engine

## Core proposition

relAIon is not a task manager that waits for a user to specify a solution.

Its larger role is to continuously translate the whole person's changing situation into possible value:

```
need discovery
  -> latent capability discovery
  -> unrealized asset discovery
  -> opportunity space
  -> possible paths
  -> feasibility and sequencing
  -> governed proposal
  -> consequence evidence
  -> learning
```

The product is the persistent understanding of the person, their world and the capabilities currently available to them. Models, applications and execution providers remain replaceable infrastructure.

The defining question is:

> What valuable possibility exists for this person now that neither the person nor the surrounding systems have yet realized?

## Beyond productivity

Conventional personal software begins with an explicit goal, project or task. relAIon begins earlier.

A person may express a need without knowing the right solution:

- more time with family
- control over finances
- a viable company
- better health
- a place to live
- a different career

The explicit statement is evidence, not a complete specification. relAIon must distinguish:

- expressed request from underlying need
- short-term intent from durable preference
- desired outcome from assumed solution
- an available capability from authority to use it
- a possible path from a legitimate action

This makes relAIon personal opportunity infrastructure, not merely personal productivity software.

## Opportunity inputs

relAIon maintains governed, evidence-backed views of:

### Needs

Explicit and inferred needs, each with provenance, confidence, time horizon, context and status. Inferred needs remain hypotheses until sufficiently supported or confirmed.

### Latent capabilities

Skills, knowledge, experience, credentials, habits, creative capacity and combinations of abilities that exist but are not currently being applied.

### Unrealized assets

Time, capital, data, devices, property, rights, access, relationships, reputation, location, contracts, memberships and other resources that may create value.

An asset being known or available does not authorize its use.

### Current reality

Commitments, constraints, health, energy, location, liquidity, deadlines, dependencies, active mandates and the capabilities exposed by connected providers.

### External possibility

Current services, markets, people, institutions, information and events that may create or close paths. External observations pass the normal relAIon evidence and admissibility boundary before they alter canonical state.

## Opportunity graph

The Opportunity Engine produces an explicit graph rather than a single opaque recommendation.

Each candidate opportunity records at least:

- the need or value it could serve
- the supporting evidence
- required capabilities and assets
- missing prerequisites
- possible paths
- dependencies and sequencing
- time horizon: now, today, tomorrow or later
- cost, risk and reversibility
- expected value and uncertainty
- affected people and competing needs
- required consent, mandate and authority
- expiry or conditions that would invalidate it

A path is a hypothesis about how value could be realized. It is not a promise, instruction or authorization.

relAIon may rank or compare paths, but it must preserve uncertainty and show material trade-offs. It must not collapse the whole person into one optimization score.

## Canonical flow

```
observations and stated needs
  -> evidence validation
  -> need hypotheses
  -> capability and asset matching
  -> constraint-aware opportunity graph
  -> possible paths
  -> feasibility, risk and timing
  -> user judgement where required
  -> RACS action envelope
  -> VAIG integrity evaluation
  -> REHT consequence-time admissibility
  -> external execution boundary
  -> effect evidence
  -> canonical learning
```

relAIon owns discovery, continuity, synthesis and proposal. It does not own execution authority.

## Governance invariants

1. An inferred need is not consent.
2. A known asset is not permission to use it.
3. A relationship is not an entitlement or capability grant.
4. A technical capability is not authority.
5. A high-value path is not automatically admissible.
6. A previous approval is not necessarily valid at consequence time.
7. Opportunity ranking must not hide uncertainty, conflicts or affected parties.
8. Only the minimum personal context necessary for a capability or proposal may be disclosed.
9. Every consequence-bearing path becomes a governed proposal and crosses VAIG/REHT before execution.
10. relAIon never executes.

This preserves the existing boundary:

```
relAIon discovers and proposes.
VAIG evaluates integrity.
REHT decides admissibility at consequence time.
Harness/Core executes outside relAIon.
Evidence returns to relAIon.
```

## Learning loop

Outcomes update the opportunity model, but do not silently rewrite the person.

relAIon records:

- what was proposed
- what the person accepted, rejected, deferred or changed
- what REHT allowed, denied or escalated
- what actually happened
- which expected value materialized
- which constraints or assumptions were wrong
- whether the need was actually served
- what should weaken, strengthen or remain unknown

Repeated behavior is not automatically a durable preference. Explicit signals outweigh implicit ones; conflicting evidence weakens confidence; unresolved uncertainty remains visible.

## Strategic implication

As agents compress implementation, the bottleneck moves from producing a specification to judgement about what is worth doing. relAIon moves one level further upstream and one level further downstream:

- upstream: discover needs, latent capabilities, unrealized assets and possible paths
- downstream: convert selected paths into governed proposals and learn from verified effects

The durable value is not the model that generates an answer. It is the continuity-bearing system that finds value the person cannot yet see and connects it to what can legitimately be done now.

## External stimulus

The initial product-management observation was that the traditional customer-need-to-specification translation layer is compressing as agents turn well-formed problems into working software. That supports the shift from implementation toward problem shaping, context curation and evaluation. relAIon generalizes the shift beyond software creation into persistent personal need, capability, asset and opportunity discovery.
